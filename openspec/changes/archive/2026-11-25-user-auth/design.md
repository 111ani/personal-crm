# Design

## Context

Сейчас запросы в `src/lib/contacts/queries.ts` и `src/lib/groups/queries.ts`, а также действия в `src/app/actions.ts` работают с общими записями. У контактов и групп нет владельца, а имя группы уникально во всей базе. Заметки и отметки привязаны к контакту. В проекте включён Next.js Cache Components, и браузерные тесты поднимают приложение отдельно со своей базой.

Выкатка уже делает копию базы, применяет миграции отдельным контейнером и проверяет `/health`. Сейчас прежнее приложение продолжает работать во время миграции, а ручной `rollback.sh` возвращает образ на текущей схеме базы.

## Goals / Non-Goals

**Goals**

- Проверять сессию на сервере во всех точках чтения и записи CRM. Сохранить обычное поведение списка, карточки, групп и напоминаний внутри аккаунта.
- Поддержать перенос заполненной базы и запуск с нуля. Собирать один образ для всех окружений.

**Non-Goals**

- Пароли, другие способы входа, профиль, роли, приглашения и предоставление доступа к записям другим пользователям.

## Decisions

- **Сессия и страницы.** Использовать Better Auth с хранилищем в PostgreSQL через Drizzle и отдельной сессией в каждом браузере. Обновлять срок до 30 дней от последнего посещения на сервере и проверять обновление cookie в реальном браузере. Проверять сессию до чтения на главной, в группах и в карточке и отдельно в каждом серверном действии, поскольку обращение к нему возможно и без открытия страницы. Корневая разметка остаётся общей, защищённые страницы и шапка получают данные из запроса. Исключить совместное кэширование персональных данных. `/health` остаётся доступным для проверки выкатки без входа. [Better Auth, сессии](https://better-auth.com/docs/concepts/session-management)
- **Запрос и проверка ссылки.** Вести запросы через один серверный путь с нормализацией и валидацией до вызова Better Auth Magic Link. Ограничить доступные обработчики Better Auth так, чтобы эти правила действовали на любой доступный способ запросить или погасить ссылку. PostgreSQL хранит историю выдач для скользящего окна в десять минут и сведения о последней действующей ссылке для адреса. Согласовать выдачу, замену и проверку ссылки при одновременных запросах. Следить за сроком 15 минут, однократным погашением и тем, чтобы отклонённый лимитом запрос не заменял действующую ссылку. Better Auth отвечает за проверку ссылки и создание сессии. Сохранять хеш ссылки, а адрес возврата брать из серверных настроек. [Better Auth, Magic Link](https://better-auth.com/docs/plugins/magic-link)
- **Письма.** Один почтовый модуль Nodemailer с настройками SMTP. Для локального запуска и CI настроить Mailpit, для сервера — Resend с защищённым соединением. Передавать настройки во время запуска. Секреты оставить в `.env`, а в `.env.example` перечислить переменные без секретов. Ссылка из письма ведёт прямо в CRM. Убрать токены из журналов запросов, ошибок и отладки почты. [Nodemailer, SMTP](https://nodemailer.com/smtp), [Resend, SMTP](https://resend.com/changelog/smtp-service)
- **Владелец в запросах.** Хранить обязательный `owner_id` в `contacts` и `groups`. Передавать идентификатор из проверенной сессии в функции чтения и добавлять его в условия запросов, включая счётчики и «Пора связаться». Проверять заметки и отметки через владельца контакта. Проверять оба конца связи «контакт — группа» и сохранять её в одной транзакции с изменением контакта. Для ввода с чужим или отсутствующим идентификатором использовать одинаковое поведение. Заменить общий уникальный индекс имени группы на уникальность по владельцу и имени без учёта регистра.
- **Почта для переноса и демо-данных.** Владелец указывает свой адрес в `CRM_OWNER_EMAIL` в `.env`. Миграция заполненной базы и команда подготовки демо-данных читают эту настройку и проверяют адрес по тем же правилам, что и при входе. В `.env.example` остаётся пустой шаблон настройки. Автотесты используют отдельные тестовые адреса.
- **Демо и браузерные тесты.** Демо-записи привязывать к настроенному владельцу. Проверки наличия и сброс демо-данных ограничить этим аккаунтом. Playwright получает письма из API Mailpit по адресату, входит в реальном браузере и продолжает использовать отдельную тестовую базу PostgreSQL. Для короткой проверки сроков подготавливать даты в тестовой базе и проверять результат в браузере или на серверном входе. Сохранить отдельный тест главного сценария. [Mailpit, API](https://mailpit.axllent.org/docs/api-v1/)

## Risks / Trade-offs

- Два запроса к одному адресу в один момент могут создать лишнее письмо или оставить две рабочие ссылки. Проверку лимита, замену и погашение проверять также при одновременных запросах. Явные сбои отправки и повторные запросы учитывать так, чтобы исключить лишние отправки.
- Старое приложение может изменить общую базу во время переноса. При первой выкатке остановить его перед копированием и миграцией. CRM на это время будет недоступна.
- Прежний образ на новой базе может открыть общие данные. Перед запуском проверять совместимость версии с базой при откате через границу первого релиза с входом.

## Migration Plan

1. Перед выкаткой подготовить настройки почты и входа. Владелец добавляет `CRM_OWNER_EMAIL` в серверный `.env` до запуска переноса. Записи DNS для Resend на стороне владельца домена.
2. Прогнать миграцию Drizzle на базе со схемой до входа и тестовыми записями. Создать таблицы авторизации, определить аккаунт владельца по нормализованной почте и заполнить `owner_id` существующих контактов и групп. Аккаунт, заведённый переносом, получает действующую сессию только после перехода по ссылке. Сделать поля обязательными и заменить индекс групп. Сохранить идентификаторы, содержимое и связи заметок, отметок и групп. Если в заполненной базе нельзя определить владельца, остановить миграцию с понятной ошибкой. Сверить данные до и после и показать миграцию владельцу до слияния.
3. При первой рабочей выкатке остановить старый контейнер приложения, снять копию и записать, какой прежний образ ей соответствует. Применить миграцию одноразовым контейнером из нового образа. После успеха запустить приложение и проверить `/health`, вход почтой владельца и пустой список с другого адреса. При ошибке сообщить о ней и остановить выкатку.
4. Подготовить и проверить ручной откат как единое переключение под блокировкой выкатки. Приложение должно оставаться остановленным, пока не подготовлена согласованная пара из копии базы до перехода и прежнего образа. Базу восстанавливает владелец через штатный сценарий restore с подтверждением и копией текущей базы. Restore сохраняет выбранную версию образа. Обычный откат образа через границу появления владельцев должен останавливаться с указанием на процедуру совместного отката.
