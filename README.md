# Личная CRM

Приложение для своих контактов: кто это, откуда знакомы, телефон и почта, заметки о том, о чём договорились.

## Что умеет

- **Список контактов** — открываете приложение и сразу видите всех людей, по алфавиту. Когда есть хотя бы одна группа, под поиском появляется ряд кнопок: «Все», группы по алфавиту и «Настроить группы» (ведёт на страницу «Группы»). Нажмите на группу — в списке останутся только её люди, над списком «Всего 3 контакта в группе «Семья»». «Все» возвращает полный список. Выбранная группа записана в адресе страницы: она остаётся после обновления, кнопки «Назад» и в закладке. Если группу удалили, откроется весь список
- **Поиск по имени** — начните печатать в строке поиска; слова можно писать в любом порядке: «Смирнова Анна» найдёт «Анна Смирнова». Если выбрана группа, ищет только среди её людей («Найдено: 1 контакт из 2 в группе «Теннис»»); выбранная группа при наборе не сбрасывается, а набранный текст не стирается при смене группы
- **Пора связаться** — блок на главной между поиском и списком: люди, с которыми не было общения дольше, чем задано в поле «Как часто общаться» их карточки. Сверху те, у кого срок наступил раньше всех; у каждого — частота и насколько просрочено: «раз в месяц · просрочено на 2 недели». Сразу видно пятерых, остальных — по кнопке «Показать всех (N)». Человек уходит из блока, когда о нём написали заметку или поставили галочку «Связались» справа в его строке. Галочка заметку не создаёт; поставили по ошибке — нажмите «Отменить» в сообщении внизу экрана, оно держится 6 секунд. Выбранная группа на блок не влияет: он показывает всех. Пока в поиске что-то набрано, блок скрыт; если связаться пора не с кем, блока нет
- **Добавление контакта** — кнопка «Добавить контакт», обязательно только имя. Сразу можно отметить группы (поле «Группы», там же «+ Новая группа»). Новый контакт подсвечивается в списке
- **Карточка контакта** — нажмите на человека в списке:
  - слева — заметки: напишите, о чём поговорили, и нажмите «Добавить заметку» (или Ctrl + Enter). Заметки хранятся с датой, новые сверху
  - справа — данные контакта: можно исправить и нажать «Сохранить изменения»
  - «Группы» — после «Почты»: все группы метками, нажмите на метку, чтобы отметить (появится галочка) или снять. Человек может быть сразу в нескольких группах. Сохраняется кнопкой «Сохранить изменения» вместе с остальными данными: не сохранили — группы не изменились. «+ Новая группа» — впишите название и нажмите «Создать» (или Enter): группа появится сразу и будет отмечена; если такая уже есть, просто отметится она. Пока групп нет, там написано «Групп пока нет»
  - «Как часто общаться» — раз в неделю, месяц, квартал, год или «Каждые … дней»: тогда в строке остаётся «Каждые», а справа появляется окошко, куда вписываете число дней от 1 до 365 — «Каждые [3] дня». По умолчанию «Не задано». Сохраняется кнопкой «Сохранить изменения» вместе с остальными данными. Под полем видно, когда пора связаться: «Связаться до 15 ноября» или «Пора связаться — просрочено на 5 дней». Срок считается от последнего общения — заметки или отметки «Связались», что было позже; если ни того ни другого ещё нет — с момента, когда задали частоту. Месяц, квартал и год — по календарю. Срок наступает с начала дня: весь день срока человек в блоке с подписью «срок сегодня», на следующий день — «просрочено на 1 день». Правка других данных (например, телефона) срок не сдвигает
  - «Связались сегодня» — галочка под строкой срока, видна, только если частота задана. Сохраняется сразу, без «Сохранить изменения»: срок считается заново от сегодня, заметка не создаётся. Поставили по ошибке — снимите галочку в тот же день, срок вернётся прежний. Если сегодня не отмечали, а раньше отметки были, под галочкой написано «Последняя отметка — 6 октября». «Сегодня» — по часам сервера: день меняется в 3 часа ночи по Москве
- **Удаление контакта** — в карточке под «Сохранить изменения» кнопка «Удалить контакт». Приложение переспросит; контакт удаляется вместе с заметками и отметками «Связались» навсегда
- **Группы** — страница «Группы»: создайте группу (например, «Семья» или «Теннис»), переименуйте или удалите. Название не повторяется (большие и маленькие буквы не различаются), у каждой группы видно, сколько в ней людей. При удалении группы люди остаются в контактах — просто выходят из этой группы
- Данные хранятся на сервере. Чтобы открыть свои контакты в другом браузере, войдите с той же почтой

## Как запустить

Нужны: запущенный **Docker Desktop**, **Node.js** и **pnpm**.

1. Если файла `.env` нет — скопируйте `.env.example` в `.env` и заполните значения. В `CRM_OWNER_EMAIL` впишите адрес, с которым будете входить как владелец. С этим адресом связываются уже существующие записи и демо-данные. Регистр букв и пробелы по краям адреса не учитываются.
2. Установите зависимости (один раз):

   ```
   pnpm install
   ```

3. Подготовьте базу (один раз). Команда запустит PostgreSQL и тестовую почту Mailpit в Docker, создаст таблицы и добавит 1000 тестовых контактов владельцу

   ```
   pnpm db:setup
   ```

4. Соберите приложение (заново — после каждого изменения кода):

   ```
   pnpm build
   ```

5. Запустите приложение:

   ```
   pnpm start
   ```

6. Откройте http://localhost:3000 и запросите ссылку на адрес из `CRM_OWNER_EMAIL`. В Mailpit откройте письмо «Вход в Личную CRM» и нажмите «Войти». Так вы увидите демо-данные. Чтобы проверить пустой список, откройте приложение в приватном окне и войдите с другим корректным адресом.

Тестовые письма можно открывать в Mailpit по адресу http://localhost:8025. Для локального входа добавьте в `.env` `BETTER_AUTH_URL=http://localhost:3000`, `SMTP_HOST=127.0.0.1`, `SMTP_PORT=1025` и `SMTP_FROM=noreply@mail.crm.example.test`. Оставьте `SMTP_USER` и `SMTP_PASSWORD` пустыми. Для `BETTER_AUTH_SECRET` сгенерируйте отдельное случайное значение командой `node -p "require('node:crypto').randomBytes(32).toString('hex')"` и впишите его в `.env`.

Остановить приложение — `Ctrl + C` в окне, где запущен `pnpm start`.

`pnpm dev` — режим разработки: сразу подхватывает правки в коде, но с 1000 контактов список открывается в десятки раз медленнее (около 15 секунд против 0,3). Для обычной работы с контактами используйте `pnpm build` + `pnpm start`.

## База данных

| Команда | Что делает |
| --- | --- |
| `pnpm db:up` | Запускает PostgreSQL и Mailpit в Docker и ждёт готовности обоих |
| `pnpm db:migrate` | Создаёт или обновляет таблицы по миграциям из папки `drizzle` |
| `pnpm db:seed` | Добавляет 1000 тестовых контактов аккаунту `CRM_OWNER_EMAIL`, если у него ещё нет контактов. Примерно у 150 задана частота общения, у части есть отметки «Связались» |
| `pnpm db:seed --reset` | **Удаляет контакты, заметки, отметки «Связались» и группы аккаунта `CRM_OWNER_EMAIL`** и заново заполняет этот аккаунт тестовыми данными. Запускайте только для локальной демо-базы |
| `docker compose ps` | Проверить, что база работает — в колонке STATUS должно быть `healthy` |
| `docker compose stop` | Остановить базу. Данные при этом сохраняются |

Тестовые контакты вымышленные. Почтовые адреса — на зарезервированных доменах `example.com`, `example.org`, `example.net`: такие адреса не принадлежат реальным людям.

## Выкатка на сервер

Рабочая CRM доступна на https://app.lena-14.ru. Тест-стенд доступен на https://test-app.lena-14.ru.

### Как выкатить новую версию

Влейте PR в `main` после успешных проверок. Остальное происходит само, примерно за 3–5 минут:

1. GitHub Actions собирает образ приложения и кладёт его в GitHub Container Registry. Имя образа — `ghcr.io/111ani/personal-crm`, тег — SHA коммита
2. Запускает две независимые выкатки одного образа. Для рабочей CRM и стенда копирует папку `deploy/` в разные каталоги и передаёт скрипту `deploy/deploy.sh` параметр `prod` или `staging`
3. На сервере скрипт для каждого окружения:
   - скачивает новый образ и проверяет, что настройки входа и почты заданы
   - перед первым переносом записей под владельца останавливает прежнее приложение
   - на проде сохраняет бэкап в `/srv/personal-crm/backups/` с именем `deploy-<SHA прежней версии>-<дата и время UTC>.dump`. Если бэкап не удался, выкатка останавливается. При первом запуске, пока базы ещё нет, скрипт пропускает бэкап. Если база уже есть, а приложение ещё ни разу не запускалось, в имени будет `unreleased`. На стенде выкатка идёт без бэкапа
   - применяет миграции базы отдельным разовым контейнером. Если миграции упали, новая версия не запускается. Во время первого переноса прежнее приложение остаётся остановленным
   - запускает новую версию
   - проверяет `/health` по HTTPS на адресе выбранного окружения
   - после успешной выкатки на прод удаляет с сервера образы старше двух недель, сохраняя текущий и предыдущий образы прода и текущий образ стенда

Ход выкатки виден в GitHub → **Actions** → **Deploy**. Проверяйте результаты `deploy (prod)` и `deploy (staging)` по отдельности. Чтобы повторить выкатку в одно окружение, выберите **Run workflow** → **Environment to deploy** и укажите `prod` или `staging`. В каждом окружении GitHub запускает по одной выкатке за раз. Сервер также блокирует параллельные операции с одним окружением.

### Первый запуск тест-стенда

1. Через `ssh crm` откройте отдельный файл настроек командой `sudo -u app-deploy bash -c 'umask 077; nano /srv/personal-crm/staging/.env'`. Для пароля базы и секрета входа сгенерируйте два разных значения командой `openssl rand -hex 32`. В `SMTP_PASSWORD` укажите отдельный ключ Resend для стенда, а в `SMTP_FROM` — подтверждённый адрес отправителя.

   ```dotenv
   POSTGRES_USER=crm_staging
   POSTGRES_PASSWORD=
   POSTGRES_DB=crm_staging
   BETTER_AUTH_URL=https://test-app.lena-14.ru
   BETTER_AUTH_SECRET=
   SMTP_HOST=smtp.resend.com
   SMTP_PORT=465
   SMTP_USER=resend
   SMTP_PASSWORD=
   SMTP_FROM=
   ```

2. Задайте пароль сайта для логина `staging`. Команда запросит пароль в терминале и запишет его хеш в файл nginx.

   ```bash
   sudo bash -c 'set -e; hash=$(openssl passwd -6); test -n "$hash"; printf "staging:%s\n" "$hash" > /etc/nginx/test-app.lena-14.ru.htpasswd'
   ```

3. Выберите самый свежий архив из списка и загрузите его в пустую базу стенда. Скрипт покажет файл и имя базы. Введите `yes`, чтобы подтвердить.

   ```bash
   sudo -u app-deploy ls -lt /srv/personal-crm/backups/
   sudo -u app-deploy bash /srv/personal-crm/staging/deploy/restore-staging.sh /srv/personal-crm/backups/ИМЯ_ФАЙЛА.dump
   ```

4. Запустите выкатку для `staging` из **Actions → Deploy → Run workflow**. Откройте https://test-app.lena-14.ru в приватном окне. Введите пароль сайта, затем запросите ссылку входа. Проверьте адрес ссылки в письме и откройте её. Войдите с адресом, которому принадлежат контакты в копии базы. Откройте прод в той же вкладке: сессия стенда должна оставить прод на странице входа.

Стек стенда — проект Docker Compose `staging` с отдельной базой, томом и локальным портом приложения `3001`. У базы лимит памяти 256 МБ, у приложения и контейнера миграций — по 512 МБ. Nginx использует отдельный сертификат Let's Encrypt с автоматическим продлением. Его конфигурация — `deploy/nginx/test-app.lena-14.ru.conf`.

Для ручного отката к прежнему образу стенда посмотрите `PREVIOUS_TAG` в `/srv/personal-crm/staging/release.env` и выполните `sudo -u app-deploy bash /srv/personal-crm/staging/deploy/deploy.sh staging SHA_ПРЕЖНЕЙ_ВЕРСИИ`. Образ должен быть на сервере и поддерживать текущую схему базы.

### Если новая версия сломалась: откат

Откат только ручной. Если предыдущая версия использует ту же схему базы, команда возвращает предыдущую версию приложения, а данные сохраняются.

```
ssh crm
sudo -u app-deploy bash /srv/personal-crm/deploy/rollback.sh
```

Повторный запуск той же команды вернёт версию, которая была до отката. Следующий push в `main` выкатит новую версию как обычно.

Если предыдущая версия была ещё без входа, `rollback.sh` остановится. Чтобы вернуться к ней, нужно восстановить базу из копии перед первым переносом и запустить соответствующую версию. Записи после того переноса исчезнут из рабочей базы. Перед заменой скрипт сохранит их в страховочную копию.

```bash
ssh crm
sudo -u app-deploy cat /srv/personal-crm/auth-baseline
sudo -u app-deploy bash /srv/personal-crm/deploy/rollback.sh --with-database /srv/personal-crm/backups/ИМЯ_ФАЙЛА.dump
```

Подставьте путь со второй строки `auth-baseline`. Скрипт покажет файл, базу и версию приложения после восстановления. Введите `yes`, только если хотите выполнить откат. После успешного запуска откройте CRM и убедитесь, что видны контакты из этой копии и приложение отвечает на `/health`.

### Восстановление базы из бэкапа

Восстановление заменяет все данные рабочей базы содержимым выбранного бэкапа. Убедитесь, что бэкап подходит к версии приложения, которая сейчас установлена. На время восстановления приложение будет недоступно.

```bash
ssh crm
sudo -u app-deploy ls -lt /srv/personal-crm/backups/
sudo -u app-deploy bash /srv/personal-crm/deploy/restore.sh /srv/personal-crm/backups/ИМЯ_ФАЙЛА.dump
```

Скрипт проверит архив и покажет путь к файлу, имя базы и версию приложения. Сверьте их и введите `yes`, чтобы продолжить. Для отмены нажмите Enter.

После подтверждения скрипт сохранит страховочный бэкап `before-restore-<SHA текущей версии>-<дата и время UTC>.dump` в той же папке, остановит приложение, пересоздаст базу и загрузит данные. После успешной загрузки он запустит тот же контейнер приложения и проверит `/health`. Если загрузка завершится ошибкой, приложение останется остановленным, а выкатка и откат будут ждать успешного восстановления. Повторите команду с исправным бэкапом или со страховочной копией, путь к которой скрипт вывел перед остановкой приложения.

После выкатки откройте лог **Deploy** и найдите `Backup saved` перед миграциями. Проверьте, что файл есть в списке выше и SHA в имени совпадает с тегом прежней версии (`PREVIOUS_TAG` в `release.env` при выкатке нового тега). После подтверждённого восстановления откройте приложение, проверьте ожидаемые контакты и заметки и сравните тег приложения до и после команды `sudo docker inspect --format '{{.Config.Image}}' prod-app-1`.

### Что где лежит на сервере

| Что | Где |
| --- | --- |
| Настройки базы: пользователь, пароль, имя базы | `/srv/personal-crm/.env`, права 600 — читает только владелец |
| Какая версия запущена сейчас и какая была до неё | `/srv/personal-crm/release.env` (пишет `deploy.sh`) |
| Скрипты выкатки | `/srv/personal-crm/deploy/` — копия папки `deploy/`, обновляется при каждой выкатке |
| Бэкапы рабочей базы | `/srv/personal-crm/backups/`, папка доступна владельцу `app-deploy` |
| Контейнеры | Docker, проект `prod`: `prod-db-1` (PostgreSQL, данные в томе `prod_db-data`) и `prod-app-1` (приложение) |
| Настройка nginx для app.lena-14.ru | `/etc/nginx/sites-available/app.lena-14.ru`, образец — `deploy/nginx/app.lena-14.ru.conf` |
| Пользователь, под которым GitHub выкатывает | `app-deploy`: без sudo, может только управлять Docker |

В серверном `/srv/personal-crm/.env` проверьте следующие настройки базы и владельца. До первой выкатки входа заполните `CRM_OWNER_EMAIL` адресом, которому должны достаться существующие контакты и группы. Если в базе есть записи, а адрес не задан или неверен, миграция остановится.

```
POSTGRES_USER=
POSTGRES_PASSWORD=
POSTGRES_DB=
CRM_OWNER_EMAIL=
```

В пароле — только латинские буквы и цифры, например вывод команды `openssl rand -hex 32`.

Для входа задайте `BETTER_AUTH_URL` с адресом рабочей CRM и свой `BETTER_AUTH_SECRET`. Для доставки писем через Resend задайте `SMTP_HOST=smtp.resend.com`, `SMTP_PORT=465`, `SMTP_USER=resend` и `SMTP_PASSWORD` с ключом Resend. В `SMTP_FROM` укажите адрес `noreply@mail.crm.<ваш домен>`, предварительно подтвердив домен отправки в Resend.

Для выкатки в настройках репозитория на GitHub (Settings → Secrets and variables → Actions) лежат: секрет `DEPLOY_SSH_KEY` — ключ, которым GitHub входит на сервер; переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` — адрес сервера, пользователь и отпечаток сервера.

Полезные команды на сервере (после `ssh crm`):

| Команда | Что делает |
| --- | --- |
| `sudo docker ps --filter label=com.docker.compose.project=prod` | Состояние контейнеров прода. Для стенда подставьте `staging` |
| `sudo journalctl CONTAINER_NAME=prod-app-1 -n 100` | Последние 100 строк журнала приложения. Для стенда подставьте `staging-app-1` |

## Для разработчика

- Next.js 16 (App Router, Cache Components), TypeScript, React 19, Tailwind CSS 4, shadcn/ui (Base UI)
- PostgreSQL 18 в Docker, Drizzle ORM: схема — `src/db/schema.ts`, миграции — `drizzle/`
- Браузер к базе не обращается: чтение — в серверных компонентах (`src/lib/contacts/queries.ts`), изменения — через Server Actions (`src/app/actions.ts`)
- После изменения схемы: `pnpm db:generate` (создаст миграцию), затем `pnpm db:migrate`
- Проверки: `pnpm typecheck`, `pnpm lint`, `pnpm build`
- Автотесты (Vitest): запустить базу `pnpm db:up`, затем `pnpm test` (один прогон) или `pnpm test:watch` (перезапуск при правках). Тесты идут на настоящей базе, но на отдельной — `<имя вашей базы>_test`: она создаётся сама, перед каждым тестом очищается, а ваши данные не трогает
- `/health` — проверка для выкатки: 200, если приложение работает и база отвечает, иначе 503
- Образ — `Dockerfile`; в нём же миграции (`node scripts/migrate.ts`) и тестовые данные (`node scripts/seed.ts`). Выкатка — `.github/workflows/deploy.yml` и `deploy/`
- Требования к фичам ведём в [OpenSpec](https://openspec.dev): действующие требования — `openspec/specs/`, фичи в работе — `openspec/changes/`, настройки (язык спек — русский, контекст проекта) — `openspec/config.yaml`. Команды в Claude Code: `/opsx:propose` — описать фичу, `/opsx:apply` — сделать, `/opsx:archive` — закрыть. На новом компьютере один раз: `npm install -g @fission-ai/openspec@latest`, обновить файлы в проекте — `openspec update`
